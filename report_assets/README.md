## 1. What the AI does

During a 10-minute pass the satellite has **one radio** and a **small battery**. Every 10 seconds the AI decides **what to transmit next**.

- **Model:** Decision Tree classifier (scikit-learn `DecisionTreeClassifier`, max depth 8)
- **Why this model:** very small (20 KB file, 185 nodes), fast (about 60 µs per decision), and explainable. The use case recommends lightweight models such as decision trees for low-power PocketQube hardware.

**Inputs (6 features)**

| Feature | Meaning | Range in dataset |
|---|---|---|
| `snr_db` | Signal strength of the link (dB) | −5 to 25 (mean 10.0) |
| `battery_pct` | Battery level (%) | 0 to 100 (mean 50.2) |
| `time_left_s` | Seconds left in the pass | 0 to 600 (mean 299) |
| `q_ttc` | Health / telemetry messages waiting | 0 to 2 |
| `q_sstv` | SSTV photos waiting | 0 to 3 |
| `q_voice` | Codec2 / M17 voice or data messages waiting | 0 to 4 |

**Output (5 classes):** `TX_TTC` send health data · `TX_SSTV` send photo · `TX_VOICE` send voice/data · `SAFE_BEACON` battery saver beacon · `IDLE` wait.

## 2. Dataset

- **Type:** synthetic, generated by `ai/train_model.py`. No real satellite data was available, as the guideline allows.
- **Size:** 5000 rows. Each input is drawn at random within the ranges above.
- **Labels:** produced by the rule-based baseline (section 3). **124 rows (2.5%) have deliberately wrong labels** (3% random noise) to imitate imperfect real data.
- **Split:** 80% training (4000 rows) / 20% testing (1000 rows), `random_state=42`.

## 3. Rule-based baseline (`ai/rules.py`)

The mission priority from the use case (TT&C > SSTV > voice/data) is written as rules:

1. battery < 20% → `SAFE_BEACON`
2. SNR < 3 dB → `IDLE`
3. health data waiting → `TX_TTC`
4. photo waiting **and** battery ≥ 50% **and** SNR ≥ 10 dB **and** ≥ 36 s left → `TX_SSTV`
5. voice waiting **and** SNR ≥ 6 dB → `TX_VOICE`
6. otherwise → `IDLE`

**How it supports the AI workflow:**
1. **Teacher:** it creates the training labels.
2. **Benchmark:** the model is compared against it.
3. **Safety net:** at run time, if battery < 20% the satellite may only send a beacon, whatever the model says (the "AI security" requirement of the use case).

## 4. Results (1000 test rows)

| Metric | Value |
|---|---|
| **Accuracy** | **94.8%** |
| Macro F1-score | 0.944 |
| Agreement with the clean rule policy | 98.5% |
| Rule baseline on the same (noisy) test labels | 96.3% (upper limit, because 2.5% of labels are wrong on purpose) |
| Model size / tree | 20.1 KB · depth 8 · 185 nodes · 93 leaves |
| Speed | about 60 µs per decision |

| Action | Precision | Recall | F1 | Test rows |
|---|---|---|---|---|
| TX_TTC | 0.94 | 0.96 | 0.95 | 221 |
| TX_SSTV | 0.92 | 0.92 | 0.92 | 99 |
| TX_VOICE | 0.94 | 0.95 | 0.95 | 173 |
| SAFE_BEACON | 0.97 | 0.92 | 0.95 | 189 |
| IDLE | 0.96 | 0.96 | 0.96 | 318 |

**Feature importance:** battery 31.9% · signal (SNR) 28.7% · health messages waiting 27.0% · voice waiting 5.3% · photos waiting 5.2% · time left 1.9%.
This matches the mission logic: battery and signal decide *whether* to send, and the health queue decides *what* has priority.

**On the demo pass** (`demo_pass_*.csv`, battery 85%): 60 decisions, **56/60 match the rule baseline**. Final actions: health data 10, photo 14, voice 18, wait 18. With battery 15% (`./exp4/mission --battery 15`) every decision becomes `SAFE_BEACON`.

## 5. Honest limitations (put these in the report)

- The data is synthetic and the labels come from rules, so the model learns to imitate the rules (98.5% agreement); it does not learn real radio physics.
- In the demo pass the model made 4 mistakes out of 60. For example, at t = 0 s (SNR −5.4 dB) it chose `TX_VOICE` where the rule says `IDLE`. The safety rule currently only covers low battery; adding an SNR check is an easy improvement.
- **Next steps:** train on real pass logs from the ground station, try reinforcement learning in simulation, and run the tree on the satellite's microcontroller.
